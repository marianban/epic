# Deterministic Pi epic

See the [overall workflow diagram](workflow.md) for a visual overview and concise descriptions of each step.

This project-local extension provides one sequential, human-gated epic:

`/epic` → Scout → Planner → run-scoped `plan.md` review → approval → Task Planner → prerequisite check/approval → (human task review/approval → independent scenario planning → Implementer → required checks → mandatory smoke for browser tasks → acceptance verification → Reviewer → post-implementation human task review) for each task → final verification.

## Installation

Load the extension from this repository with Pi, or install the project as a Pi package after reviewing the code. The extension entry point is `pi/extensions/epic/index.ts`. Copy `pi/epic.config.example.json` to `.pi/epic.config.json` to configure commands and role models.

Each enabled role runs in a separate `pi --mode json --no-session` process. Model/provider profiles are configured independently in the epic config. All roles except the Implementer are instructed to inspect rather than modify the project and cannot use edit/write tools. When loaded from another directory with `pi -e`, bundled role prompts are used automatically; project-local `.pi/agents/*.md` files override them.

Execution sandbox prerequisites are `rg` on macOS, and `rg`, `bubblewrap` (`bwrap`), and `socat` on Linux. Native Windows execution is unsupported; use WSL.

The epic lifecycle is represented by a typed XState v5 actor. The root machine owns planning, prerequisites, sequential task execution, escalation, final verification, and terminal states. Task execution is an invoked child actor with explicit approval, implementation, checks, semantic review, repair, and human-review states. Commands send domain events through the epic runtime adapter; they cannot bypass machine guards.

## Live inspection

The epic can be visualized while it runs with Stately Inspector. Set `inspector.enabled` to `true` in `.pi/epic.config.json`; the extension starts a local WebSocket bridge on port `8080` and opens the inspector automatically. The bridge remains available across epic commands for the lifetime of the Pi extension process. Set `inspector.port` to use another port or `inspector.autoOpen` to control browser opening. Inspection is disabled by default, and context snapshots are sanitized before they are sent to the inspector. For one-off debugging, `PI_EPIC_INSPECTOR=1` enables it and `PI_EPIC_INSPECTOR=0` disables it; the corresponding environment variables can override the port and auto-open setting.

The inspector shows root and child actor transitions as a live state-machine and sequence view. It is intended for local debugging; do not enable it for epics whose event or context data must remain private.

The initial Scout is not necessarily the only discovery pass. A Planner may return a focused `needs_more_context` request; the engine sends only those questions to another read-only Scout and gives the merged evidence back to the Planner. This loop is bounded by `maxScoutRounds` (default: 3). After plan approval, the Task Planner receives the hash-verified plan plus epic/repository context and decomposes it into ordered, independently reviewable tasks.

## Commands

In Pi fullscreen mode (`"tuiMode": "fullscreen"` in `.pi/settings.json` or `~/.pi/agent/settings.json`), the active dashboard fills the space remaining after Pi’s prompt, footer, status rows, and other widgets, retaining Pi’s required one-row conversation minimum. Its height adapts to terminal resizing and multi-line prompts. Scroll over it with the mouse wheel or trackpad, or use `Alt+PageUp` / `Alt+PageDown` and `Alt+Home` / `Alt+End`. A scrollbar and row counter appear when content overflows. Keyboard navigation brings the focused panel or checkpoint control into view; refreshes preserve your scroll position. Regular mode retains the expanded dashboard and terminal-owned scrollback.

- `/epic <epic>` starts one epic, writes the run's `Epic.md`, and always pauses after writing its run-scoped `plan.md`.
- `/epic-status` shows persisted state and the pending human action.
- `/epic-resume` retries failed acceptance planning in a fresh bounded batch, revalidates a task at its verification checkpoint, or resumes the current workflow boundary.
- `/epic-exit` hides the Epic widgets without changing persisted Epic state.
- `/epic-approve-prerequisites` applies the exact prerequisite commands discovered for the repository after human approval.
- `/plan-review` extracts standalone or trailing inline `R:` comments and asks the Planner to revise.
- `/plan-revise` forces a Planner revision.
- `/task-approve` continues the current task review: it refines `R:` findings automatically, or approves the task when no findings remain.
- `/task-review` refines pre-implementation task-artifact `R:` findings. After implementation, code repairs require an explicit `/task-repair` grant; ordinary resume does not grant attempts.
- `/plan-approve` continues plan review: it refines `R:` findings automatically, or validates, hashes, and approves the plan when no findings remain.

Plan approval records a hash, then starts implementation. The approved plan hash remains in persisted state so implementation cannot be entered through an unapproved path.

After approval, the Task Planner writes the JSON task manifest to `.pi/epics/runs/<epic-id>/artifacts/tasks.json` and one Markdown file per task under `.pi/epics/runs/<epic-id>/tasks/`. Before each task’s implementation, the epic pauses for human review of its artifact. Human findings are added as `R:` lines and revised by the task reviewer through `/task-review`; implementation cannot begin until `/task-approve` is run. After implementation and semantic review, the epic pauses again for human review; the immutable verification report shows every criterion and the current readiness. Further repairs require an explicit bounded grant before the task can advance.

## Persistence and checks

Task verification runs in stages: fast checks, full checks, then browser/acceptance verification and independent review. A failed or errored check suite blocks all later stages. Actionable check failures trigger the existing bounded repair loop; infrastructure-only failures stop for human review after any applicable infrastructure retry. Every repair restarts verification at fast checks, so later edits cannot reuse earlier passing results. All stages share the task's existing repair, infrastructure retry, and time allowances.

Runs are stored under `.pi/epics/runs/<epic-id>/`, with atomic `state.json`, append-only `events.jsonl`, detailed `epic.log`, per-invocation filtered diagnostic JSONL files under `agent-runs/`, `Epic.md`, the active `plan.md`, task artifacts, and plan revisions. `tasks/` contains only reviewable Markdown task files, including human `R:` comments. `artifacts/` contains the JSON task manifest, verification ledgers, command results, browser probes, screenshots, traces, and conclusions. Handled `R:` comments are removed when the task Markdown is revised. Each agent diagnostic log retains complete prompts, responses, tool starts and results, lifecycle events, errors, and unexpected output while discarding redundant streaming and aggregate records. Retained records are written incrementally to a new private file for every role invocation so they remain available if the parent process crashes. `.pi/epics/` owns all run artifacts, including the active plan.

Successful check progress and dependency JSON are retained in check artifacts rather than reported as findings. Explicit warning/error lines remain findings; failed checks retain their diagnostic output. Reviewer prompts, repair feedback, and check-completion logs use compact summaries, with bounded failure previews and artifact references instead of repeated raw output or domain snapshots. Full verification evidence remains in the run artifacts.

`state.json` contains a versioned hierarchical XState persisted snapshot together with durable epic context and artifact references. The current schema/machine version is `12/14`. Older or malformed snapshots, including schema 11 / machine 14, are reported as incompatible and are not silently migrated; start a new epic unless an explicit migration is added later.

Fast checks include `git diff --check`, dependency installation when `package.json` exists, and configured/discovered typecheck, lint, and focused tests. Full checks include dependency installation, configured/discovered tests and build, plus Fallow when configured. Prerequisite installation uses the repository lockfile when present. During task verification, the install gate checks installed dependency health with `npm ls --all --json` rather than reinstalling and changing candidate inputs. Every command has a timeout and bounded output. Missing package scripts are not invented as failures; configure repository-specific commands explicitly when they are required gates. Each decomposed task declares `requiredChecks`, `deferredChecks`, and a dependency-based `reason`; task-local suites execute only required checks, while other discovered checks are skipped. Deferred checks are recorded as skipped for that task and are always run by final verification.

Tasks provide suggested verification commands in `verification` and separate human inspection and interaction instructions in `manualReviewSteps`. Verification commands are advisory, not a command allowlist; acceptance criteria and `requiredChecks` remain mandatory. Tasks with browser-observable runtime behavior declare the stable `browser-smoke` check. The Implementer chooses a development-server command suitable for the implemented repository and returns a structured launch specification with an executable, arguments, loopback HTTP(S) URL, and CSS readiness selector. The command need not match the planner's suggestions. The Implementer does not start the server. During each verification cycle, the epic runtime launches and supervises that process, waits for HTTP readiness, and uses its own `playwright-core` dependency with an installed Chrome or Chromium executable. Smoke verification waits for the declared CSS readiness selector and rejects page exceptions, console errors, failed same-origin requests, same-origin HTTP errors, page crashes, and timeouts before semantic or human review. The browser and server are stopped on every exit path, and results plus a successful screenshot are stored with the run artifacts.

Browser discovery prefers `checks.browserSmoke.executablePath`, then documented Chrome/Chromium installation locations, then compatible executables on `PATH`. Discovery never downloads a browser or silently skips the gate. Task verification operations receive the remaining shared time allowance. Legacy standalone smoke helpers retain their configured startup/navigation/selector settings; these do not create separate task verification allowances.

After plan approval, the epic checks for a Git repository and declared Node dependencies. In a new or non-Git directory it proposes `git init`; when `package.json` dependencies are missing it proposes the appropriate lockfile-aware install command (`npm ci`, `npm install`, `pnpm install`, or `yarn install`). These repository-level prerequisite commands are persisted in the run artifacts and never execute until `/epic-approve-prerequisites` is run. If an approved implementation task creates its own manifest and explicitly includes dependency installation, the writable Implementer may run that task-local install inside its OS sandbox.

Acceptance scenarios are planned independently before implementation by the `verification-planner` agent. Its system instructions are in `verification-planner.md`; it reads code and dependency contracts and returns one valid JSON object with the frozen criteria and explicit browser-step fields such as `{"action":"inspect","expression":"document.querySelector('#game-container') !== null"}`. It does not run acceptance checks or start browser resources. The `verifier` agent uses separate execution instructions in `verifier.md` and a task prompt containing the accepted plan to execute browser checks after implementation. `maxAcceptancePlanRepairs` defaults to 2 (one initial call plus two corrections), accepts zero, and is persisted per epic. Only invalid JSON or scenario-contract failures receive automatic corrections with field-specific validation issues. Invocation, timeout, storage, and persisted-criteria failures pause immediately. These calls never consume verification infrastructure retries, code repairs, or the verification deadline.

Configure these agents independently under `agents.verification-planner` and `agents.verifier`. Existing `agents.verifier` overrides now affect execution only; they are not copied to the planner. Project-local `.pi/agents/verifier.md` overrides should contain execution instructions only; customize planning through `.pi/agents/verification-planner.md`.

Failed or interrupted planning pauses at `acceptance_planning_failed`, with diagnostics and a **Retry acceptance planning** action using `/epic-resume`. Task approval and report-bound decisions are unavailable there; no acceptance report is produced. Resume retains the approved task and frozen criteria, starts a fresh bounded batch, and proceeds to implementation only after a valid plan is persisted. Reopening a planning failure preserves it; reopening interrupted planning pauses without running agents. A valid plan already persisted before interruption is reused on explicit resume. Attempt events retain batch/attempt IDs, validation issues, agent invocation IDs, and available log references.

Task verification persists a task-owned allowance ledger, versioned criterion/scenario plans, cycle evidence, and immutable JSON/Markdown human reports. `maxTaskRepairs` defaults to 6, `maxTaskInfrastructureRetries` to 1, and `taskVerificationTimeoutMs` to 1800000. Counts may be zero. Obsolete phase-specific repair settings are rejected.

Repairs and infrastructure retries are charged before invocation. The shared deadline starts at first verification after initial implementation. Active downtime counts; human-checkpoint waiting does not. Resume revalidates with remaining allowances; interrupted invocations remain charged. During verification, exhaustion, cancellation, timeout, and tool failures produce a report instead of automatically accepting or editing the application. Exit remains UI-only.

Ordinary `/task-approve` requires every manual step to pass and no actionable failures. A completed nonempty manual checklist can resolve incomplete automated evidence without additional confirmations; the original report remains unchanged. Use `/task-repair` for recorded failures:

- `/task-repair` takes no arguments. It uses the current task's latest report, grants one additional repair attempt and five additional minutes, and resumes verification and repair of unresolved issues. It rejects arguments and an already verified task unless the current manual checklist contains failures. Failed manual steps and observations are sent to the Implementer before reverification. Usage history is retained.

To review later, use `/epic-exit` to hide the dashboard. The task remains awaiting review without recording a decision.

Verification is advisory. Each cycle has a unique attempt identifier; evidence and human decisions are bound to that attempt and its report, not a hash of candidate contents. Source, dependency, configuration, and generated-file changes do not discard results or block decisions or checkpoints. Rerunning verification creates a new attempt and report requiring a fresh acceptance decision. Acceptance criteria remain frozen for the task.

Scripted browser scenarios and verifier `browser_verify` tools share one runtime-owned server/browser scope per cycle, with isolated contexts per scenario. Interactions retain console errors, exceptions, failed same-origin requests, screenshots, and traces. The loopback bridge is authenticated and closed with the scope. Static/local commands and genuine human-only obligations also receive explicit evidence entries.

For `agent_browser` obligations, the plan fixes the expected behavior and leaves the verifier free to choose probes. Planned steps are optional suggestions. Every `browser_verify` call opens a fresh isolated page, runs its complete setup/actions/observations, and closes it; there are no browser session IDs or continuation between calls. The model can inspect a result and submit an adjusted probe with repeated setup. Browser tools execute sequentially.

Configure `agents.verifier` with an image-capable model. The tool checks the selected model's declared image-input support and fails explicitly if support is absent or unknown; it never substitutes a model or silently drops requested images. Screenshots are adaptive, delivered as image content to that same verifier model. No extra vision agent is used. Image payloads are omitted from diagnostic logs; PNG artifacts and evidence metadata remain available.

Probes support `click`, `press`, `text`, `visible` (selector/value), `pointer` (x/y), `key_down`/`key_up` (key), `wait` (durationMs), and arbitrary `observe`/`inspect`/`fixture` expressions. Fixtures establish starting state and cannot prove an interaction. For game input, `mouse_down`/`mouse_up` require an explicit `button` (`left`, `middle`, or `right`) and act at the current pointer position. `click_at` requires `x`, `y`, and `button`; coordinates are viewport CSS pixels, not canvas-local or screenshot pixels. Use `pointer` between mouse-down and mouse-up to drag. `hold` accepts a non-empty list of unique `keys` and `durationMs`, for example `{"action":"hold","keys":["ArrowRight","Space"],"durationMs":300}`. It presses the keys together and releases them in reverse order, including on failure or cancellation. Do not overlap these keys with keys already held by `key_down`. To capture or observe while keys remain held, use key_down, intermediate steps, then key_up. Both waits and holds are bounded to 10000ms and the remaining shared deadline. Add `{"action":"capture","count":1,"intervalMs":0}` at any desired point for a viewport PNG, optionally with `"selector":"canvas"` for a crop. Timed sequences use count > 1 and a positive intervalMs. Each probe permits at most 12 frames and 10000ms of capture sequence intervals. Motion observations must come from the same probe; separate fresh pages are separate executions.

Use `{"action":"resize","width":900,"height":900}` to change the actual viewport on the same page. It records actual before/after viewport dimensions and errors if the requested size was not applied. Measure the application layout before and after, allowing layout to settle within the remaining deadline; viewport changes alone do not prove responsive behavior. Page expressions run inside the webpage, so `window.resizeTo` and synthetic resize events are not substitutes.

When no predefined action fits, `{"action":"playwright","code":"await page.getByRole('checkbox').check({ timeout: timeoutMs }); return await page.getByRole('checkbox').isChecked();"}` executes an async JavaScript body with the runtime-owned Playwright `page` and remaining `timeoutMs`. Return JSON-serializable measurements, which receive ordinary observation IDs; custom code cannot itself pass an obligation. Code and returned measurements are retained in the probe artifact and interactions in the trace. Errors, cancellation, and deadline expiry remain probe errors. Await all work, use only the supplied page, and leave resource creation/cleanup to the runtime. Use `capture` steps for image evidence and separate timed steps for motion evidence. Custom code follows the same real-interaction and fixture rules. This facility executes trusted verifier code and is not a security sandbox; it does not expose module imports or Node globals as part of its supported interface.

`browser_verify` returns runtime-owned probe, observation, and image IDs plus recorded actions, timestamps, values, assertion results, and errors. It never independently passes an obligation. Use `browser_conclude` with obligationId, outcome (pass/fail/likely-fail/inconclusive), evidenceIds, explanation, limitations, and basis (observations/visual/motion). Cite measured observation/image IDs from this obligation, attempt, and verifier invocation. Visual conclusions require image IDs; motion requires at least two timed records from one probe and a temporalComparison explanation. When combining multiple probes, supply separateExecutions acknowledging their independent page state. Inconclusive conclusions require gap (blocked/not_attempted/inconclusive). Missing conclusions remain unresolved.

A canvas being visible, input dispatch succeeding, elapsed time, screenshot capture, or inspect:true is not proof of gameplay. Choose a probe that would fail if the expected behavior were broken. For example, measure paddle position before/after a held key, compare ball velocity across a real collision, or inspect lives before/after a miss. If observation is unreliable, report inconclusive and limitations rather than substituting a weaker passing assertion. The verifier can correct faulty probes within the invocation without spending an implementation repair; application/runtime errors remain recorded and prevent passing the affected obligation in that cycle. New probes invalidate an earlier conclusion for that obligation until explicitly concluded again. Every probe and conclusion retains its immutable artifact. Reports show measured facts separately from model interpretations, and semantic review inspects the actual evidence rather than trusting pass labels. These checks improve traceability but do not guarantee every model interpretation is correct. Automated scenarios still execute prescribed steps and require assertions.

The repository-owned `tests/fixtures/` counter exercises the release gate: startup smoke passes on faulty behavior, clicking exposes an exception, a charged test repair fixes it, and all checks rerun. `npm test` requires an installed Chrome/Chromium and local server access; the real-browser gate is never skipped. No external game project is required.

## Security boundaries

All agent processes and acceptance verification commands run inside the same OS sandbox: macOS `sandbox-exec` or Linux `bubblewrap`. Writes are limited to the target repository, temporary directories, and Pi's global agent directory (needed for Pi settings and credential lock files). Writes to `.git`, `.pi/epics`, and configured sensitive paths are denied; network access is unrestricted. This permits build outputs and caches anywhere in the repository without predicting output paths. Commands are not filtered by destructive-command keywords: the sandbox enforces filesystem containment, while role instructions define the intended work. Non-implementer roles still cannot use the edit/write tools, but shell commands can modify ordinary repository files. All roles can modify global Pi settings or authentication storage and reach external services within this policy; review configured commands and role models before trusting a project-local epic. Native Windows is unsupported; run Pi from WSL. Sandbox setup failures stop execution without an unrestricted fallback. Repository-level prerequisite commands remain a separate execution path and require the dedicated human approval command; an explicitly approved task-local install is permitted for the Implementer.

### Interactive manual review

After implementation, manual review steps form a persisted checklist. Every new report starts with all items **Not checked**. Use ↑/↓ to select a step and Space to cycle **Not checked → Passed → Failed → Not checked**. Enter edits an observation; selecting Failed opens the editor and requires nonblank feedback. Cancelling leaves the saved item unchanged. Tab moves between the checklist and action buttons.

One **Continue** action derives its outcome from the saved checklist. Failed manual steps or actionable automated failures mean **request fixes**: grant one repair attempt plus five minutes, including failed steps and observations when present. With unchecked manual steps, Continue is disabled. Once every manual step passes and no actionable failure or likely failure remains, Continue approves the task immediately, even when automated evidence is incomplete. There are no per-limitation confirmations or reason prompts. Approval records the user's manual verification without rewriting automated evidence. If there are no manual steps, incomplete automated evidence cannot be approved through the checklist.

Edits are saved before they appear as completed. Exit and reload preserve them. **Review history** shows saved observations from previous reports; a repair produces a fresh unchecked checklist. The review dashboard offers manual review and acceptance, with **Repair** available for actionable failures or failed manual checks. Evidence gaps alone do not offer repair. Ordinary resume does not turn manual failures into passes or submit them as new repair requests. Interrupted charged repairs are not automatically repeated; an explicit grant is required.

Persistence schema/machine versions **12/14** are required. Existing **11/14**, **10/14**, and older runs are incompatible; no migration is applied and existing run artifacts are not modified.

Evidence outcomes are `pass`, `fail`, `likely-fail`, and `inconclusive`. A `likely-fail` records an observed contradiction while a specific uncertainty prevents confirmation. It requires cited evidence and `suspectedFailure` fields `contradiction`, `uncertainty`, and `confirmationCheck`. It blocks approval, including after checklist completion, but does not alone trigger or authorize an implementation repair. Investigate and obtain a new verification result, or record a confirmed manual failure to request fixes. `inconclusive` retains gap classifications for blocked, not attempted, human-only, and inconclusive checks. Older `unverified` evidence is incompatible; no automatic conversion or reclassification of historical runs is performed.
